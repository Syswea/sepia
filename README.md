# Sepia — 基于 CUDA VMM 的推理原型执行计划

> 执行周期：8–10 周  
> 目标平台：Intel 13600 + NVIDIA RTX 4070（12 GB 显存）  
> 项目状态：规划阶段，以下为详细执行路线图

---

## 1. 项目目的

验证一个核心假设：**在 Transformer 推理过程中，让 KV Cache 使用固定不变的逻辑地址，仅动态重映射其背后的物理显存，可以在保持 CUDA Graph 高复用率的同时，减少显存碎片、避免不必要的重捕获，并改善动态 batch 与长上下文场景下的性能与显存表现。**

最终交付物包括：

1. 一个独立的、可运行的 Sepia 推理原型（模型可先用 GPT-2，再扩展到量化 LLaMA3-8B）。
2. 一套 VMM 内存管理层：`VMMAllocator` + `KVBlockManager`。
3. 与 vLLM/`cudaMalloc` 基线对比的性能数据。
4. 一份技术报告，说明方案、实现、结果与结论。

---

## 2. 背景与问题

| 问题 | 说明 |
|------|------|
| KV Cache 地址变化 | vLLM/SGLang 的 KV Cache 由物理显存分配器管理，每次分配的地址可能不同。CUDA Graph 对地址敏感，地址变化会导致重捕获或回退到 eager 模式。 |
| 显存碎片与 OOM | 动态 batch、长上下文场景中，频繁分配/释放导致碎片，12 GB 显存下更容易 OOM。 |
| 逻辑与物理解耦 | CUDA VMM API 支持先预留虚拟地址，再把物理内存动态映射到固定逻辑地址，逻辑地址对外保持不变。 |
| 换入换出能力 | 12 GB 显存无法容纳超长上下文时，可先把不活跃块的数据拷贝到 CPU 内存，再解映射并释放物理显存；逻辑地址保留，未来再映射并拷回。这降低 GPU 显存占用，但会增加 CPU 内存占用。 |

## 3. 实验设计

### 3.1 自变量

| 变量 | 取值 |
|------|------|
| KV Cache 管理方式 | 基线：`cudaMalloc` / vLLM；实验：Sepia VMM（固定逻辑地址 + 动态物理映射） |
| Batch Size | 1、8、32，以及 1–32 随机动态变化 |
| 上下文长度 | 短上下文 512 tokens；长上下文 16K tokens（仅当所选模型原生支持，见 3.5） |
| 输出长度 | 128 tokens（固定负载）；长上下文场景可单独定义 |

### 3.2 因变量与测量指标

| 指标 | 定义 | 备注 |
|------|------|------|
| TTFT | 首 token 延迟 | 越低越好 |
| TPOT | 每个 token 的平均生成延迟 | 越低越好 |
| P99 延迟 | 请求延迟的 99 分位 | 重点指标 |
| 吞吐量 | tokens/s | 固定 batch 下重点对比 |
| 显存占用峰值 | 推理过程中的 `nvidia-smi` 最大值 | 越低越好；但仅在按需映射/换出场景下预期 Sepia 更低，见 3.6 |
| CUDA Graph 命中率 | 无需重捕获即可直接重放的次数占比 | 越高越好 |
| OOM/完成率 | 是否 OOM，任务能否完成 | 长上下文场景关键指标 |

### 3.3 对照组

| 组别 | 配置 |
|------|------|
| 基线组 | 同模型、同负载，使用 `cudaMalloc` 管理 KV Cache 或使用 vLLM 默认 block manager |
| 实验组 | 同模型、同负载，KV Cache 由 Sepia 的 VMM `KVBlockManager` 管理 |

控制变量：模型、输入输出长度、batch 序列、CUDA 版本、驱动版本、GPU 时钟策略应保持一致。

### 3.4 成功标准

| 编号 | 标准 |
|------|------|
| S1 | `VMMAllocator` 能完成 256 MB 物理块的分配、映射、读写、解映射；重复 1000 次无泄漏。 |
| S2 | `KVBlockManager` 能完成 block 的分配与释放；释放后逻辑槽位可复用且地址不变；重复 10000 次无泄漏。 |
| S3 | 端到端推理输出与 `cudaMalloc` 基线完全一致。 |
| S4 | 固定 BS=8 场景下，Sepia P99 延迟不差于基线 10% 以上。 |
| S5 | 动态 BS 1–32 场景下，Sepia P99 延迟优于基线 10% 以上，CUDA Graph 命中率显著提升。 |
| S6 | 长上下文场景（长度在模型有效上下文范围内）：基线因显存分配失败或回退严重时，Sepia 能完成推理。 |

### 3.5 上下文长度与模型有效长度（重要约束）

上下文长度不能随意超过模型训练时的有效长度。模型能接受的最大序列长度由预训练/微调时的位置编码决定（如 RoPE 的训练长度或经过 YaRN、LongRoPE 等外推/插值缩放后的长度）。若直接把 16K tokens 喂给一个训练长度为 8K 的模型，可能不会报错，但位置超出训练分布，输出质量与结论有效性都会失真，不能作为公平基准。

因此长上下文实验遵循以下规则：

1. 优先选择**原生支持 ≥16K** 且 12 GB 显存可承载的模型，例如 Mistral 7B v0.2（32K）、Qwen2.5-1.5B/7B（32K 及以上）等，或使用经过 YaRN/LongRoPE 缩放并明确记录方法的模型。
2. 若候选模型在 12 GB 显存上无法支撑 16K，则选择其最大有效长度作为测试长度，不强行超出。
3. 若只验证 VMM 换出/换入能力而暂时没有合适模型，使用**合成 KV Cache 负载**：按目标模型层数、KV 头数、头维度计算每 token KV Cache 字节数，直接在 VMM 层做超显存容量压力测试，不涉及端到端生成。
4. 任何 OOM 预期都必须基于显存预算计算，而不是假设：权重显存 + 激活显存 + KV Cache 显存 = 总需求；当总需求超过 GPU 可用显存时才预期 OOM。KV Cache 字节数可按“2 × 层数 × KV 头数 × 头维度 × 精度字节数 × token 数 × batch size”估算。

### 3.6 Sepia 的显存占用预期（澄清）

Sepia 的软件 MMU 本身**不会**让同样活跃的 KV Cache 占用更少显存：

1. 当所有 KV block 都被使用且已映射时，Sepia 的物理显存占用与 `cudaMalloc`/vLLM 基线相当；VMM 的设备页表还会带来少量额外开销。
2. Sepia 可能降低**峰值显存**的场景只有两类：
   - **按需映射**：只为当前真正需要的 block 分配并映射物理显存，而不是像基线那样按 `max_model_len` 预先分配整个 KV 池。
   - **换出**：把不活跃 block 的数据先拷贝到 CPU 内存，再解映射并释放 GPU 物理显存；该 block 的 GPU 显存暂时被释放，但 CPU 内存占用增加。换入时需要重新分配物理显存、映射并拷回。
3. 本项目 `VMMAllocator`/`KVBlockManager` 的元数据（block 表、映射表、空闲队列）应设计为**主机内存**数据结构，不占用设备显存。
4. 设备侧 VMM 页表由驱动管理，不是我们的元数据；其开销较小（按分配粒度计算条目数，例如 2 MB 粒度下 12 GB 约几千个条目），但测量显存时应计入总账。

结论：**Sepia 的显存收益来自“不映射不需要的物理块”和“换出”，不来自 MMU 本身。** 基准对比时不应把“显存占用更低”作为无条件预期。

### 3.7 模块职责分工（架构确认）

| 模块 | 角色 | 拥有什么 | 负责什么 | 不负责什么 |
|------|------|----------|----------|------------|
| `VMMAllocator` | 机制层，唯一直接调用 CUDA VMM API 的模块 | 固定虚拟地址池、物理显存块池（`cuMemCreate` 句柄）、物理块空闲列表 | 预留虚拟地址；创建/释放物理内存；把物理句柄映射到指定逻辑地址 / 从逻辑地址解映射；设置访问权限；查询物理块状态 | 不理解 KV block、引用计数、CUDA Graph |
| `KVBlockManager` | 策略层，决定“哪个逻辑槽位挂哪块物理内存” | block id 到逻辑槽位/物理句柄的映射表、引用计数、空闲槽位队列 | 按需分配/释放 block；调用 `VMMAllocator` 完成映射/解映射；对外提供固定逻辑地址；回收和复用逻辑槽位 | 不直接调用 `cuMem*`，不直接管理物理块池 |
| CUDA Graph / 推理循环 | 使用方 | 只认 KV block 的固定逻辑地址 | 重放前确保映射已生效；重放后同步并决定是否延迟解映射 | 不感知物理地址变化 |

一句话总结：**KVBlockManager 决定“哪个 KV block 需要挂载/卸载”，VMMAllocator 执行“怎么把物理显存挂到固定逻辑地址上”。** CUDA Graph 始终只见固定逻辑地址，物理地址变化被前两层屏蔽。

需要注意：**Kernel 运行时不存在“软件解析虚拟地址”的过程。** CUDA Graph 重放时，kernel 直接访问固定虚拟地址，由 GPU MMU 按 `cuMemMap` 已建立的页表自动翻译到物理页。`VMMAllocator` 维护的“虚拟地址 → 物理块”映射表只在主机侧用于分配、释放、换入换出和调试，不在 GPU 访问路径上，否则会拖慢推理。

### 第 2–3 周：VMMAllocator 核心层开发

**目标**：实现一个可复用的 CUDA VMM 内存分配器，提供虚拟地址预留、物理块分配、映射/解映射能力。

| 阶段 | 任务 | 具体内容 | 产出 |
|------|------|----------|------|
| 第 1–2 天 | 项目骨架 | 创建 CMake 工程，链接 CUDA Driver API（`libcuda.so`），建立目录结构 | 可编译的空项目 |
| 第 3–4 天 | 封装 VMM API | 封装 `cuMemAddressReserve`、`cuMemCreate`、`cuMemMap`、`cuMemSetAccess`、`cuMemUnmap`、`cuMemRelease`、`cuMemAddressFree` | 头文件与实现文件 |
| 第 5–7 天 | 内存池实现 | 预留 2 GB 虚拟地址范围；实现物理内存块的分配、映射、解映射接口 | 单元测试通过 |
| 第 8–10 天 | 错误处理与诊断 | 统一错误检查、打印映射表状态、记录每次 API 调用的参数与返回值 | 可快速定位失败原因 |

**接口能力要求**：

- 预留一段固定虚拟地址范围，对外暴露其起始地址。
- 按请求大小分配物理内存，并映射到指定逻辑地址。
- 解映射时释放物理内存，但逻辑地址保持不变。
- 支持查询当前映射状态与物理块占用情况。

**验收标准**：

- [ ] `allocate(256MB)` 返回非空逻辑地址。
- [ ] 在该地址上可执行 `cudaMemset` 与自定义 kernel，无报错。
- [ ] `deallocate` 后物理显存被释放，逻辑地址保持可再次映射。
- [ ] 重复分配/释放 1000 次，`nvidia-smi` 显示显存不增长。
- [ ] 单元测试覆盖正常路径与错误路径（如映射未对齐地址、未设置访问权限等）。

**常见陷阱**：

- 物理内存分配必须对齐到 `cuMemGetAllocationGranularity` 返回的粒度。
- `cuMemSetAccess` 必须调用，否则内核访问该地址会报错。
- `cuMemAddressReserve` 只预留虚拟地址，不占物理显存。
- 解映射前确保流上的访问已结束，避免使用已解映射地址。

### 第 4 周：KVBlockManager 开发

**目标**：在 VMMAllocator 之上实现固定逻辑地址的 KV block 管理器，支持 block 的分配、释放与复用。

| 天 | 任务 | 具体内容 | 产出 |
|----|------|----------|------|
| D1–D2 | 定义 block 结构 | 设计 `KVBlock` 元数据：block id、逻辑地址、物理句柄、大小、引用计数、映射状态 | 数据结构定义 |
| D3–D4 | 分配逻辑 | 从 VMMAllocator 申请物理内存，映射到第一个空闲逻辑槽位 | `allocate_block` |
| D5–D6 | 释放逻辑 | 解映射、释放物理内存、把逻辑槽位放回空闲队列 | `free_block` |
| D7 | 映射表维护 | 维护 block id 到物理句柄、逻辑地址的映射表，支持状态查询 | 查询接口与调试输出 |

**验收标准**：

- [ ] 第 1 个 block 分配到 slot 0。
- [ ] 第 2 个 block 分配到 slot 1，且两个 block 的逻辑地址连续。
- [ ] 释放 slot 0 后再分配，能复用 slot 0 且逻辑地址不变。
- [ ] 分配/释放循环 10000 次，显存无泄漏。
- [ ] 支持并发安全（如后续需要多线程访问时）。

### 第 5–6 周：CUDA Graph 集成

**目标**：把 VMM KV block 管理器接入一个端到端推理循环，验证“逻辑地址固定 + 物理地址动态重映射”方案。

| 阶段 | 任务 | 具体内容 | 产出 |
|------|------|----------|------|
| 第 1–3 天 | 建立基线 | 用 PyTorch 加载 GPT-2，使用 `cudaMalloc` 管理 KV Cache，捕获 CUDA Graph | 纯 PyTorch 基线版本 |
| 第 4–6 天 | 替换内存管理 | 将 KV Cache 分配替换为 `KVBlockManager` | 端到端输出与基线一致 |
| 第 7–10 天 | 实现重映射流程 | 推理循环内完成：查 block 映射表 → 挂载物理内存 → 重放 CUDA Graph → 同步 → 按策略解映射 | 完整推理循环 |

**重映射流程要求**：

1. 每次推理前根据所需 token 数分配 block，得到固定逻辑地址。
2. 将输入 token、位置信息、KV Cache 逻辑地址作为图输入。
3. 重放前把物理内存映射到对应逻辑地址。
4. 重放后同步，再决定立即解映射或延迟解映射。
5. 逻辑地址在整个生命周期内保持不变。

**验收标准**：

- [ ] 单次推理输出与 `cudaMalloc` 版本完全一致。
- [ ] 连续 10 次推理，每次分配不同数量 block，输出仍一致。
- [ ] 用 Nsight Systems 能观察到每个推理周期包含 1 次 `cuMemMap` 与 1 次 `cudaGraphLaunch`。
- [ ] 当映射未命中时能正确回退，不产生静默错误。

**风险提示**：

- CUDA Graph 捕获复杂时，先从单层/小模型开始，再逐步扩展到全模型。
- 延迟解映射策略可能暂时占用更多显存，需要设置阈值。
- 若 GPU 上 `cuMemMap` 延迟过高，优先优化映射缓存而不是重写方案。

### 第 7 周：性能测试与对比

**目标**：在统一负载下对比基线组与实验组，收集关键指标并给出归因分析。

| 天 | 任务 | 具体内容 | 产出 |
|----|------|----------|------|
| D1–D2 | 基线测试 | 用 vLLM（不加 VMM）跑固定负载 | 基线数据 |
| D3–D4 | Sepia 测试 | 相同负载用 Sepia Runtime 跑 | Sepia 数据 |
| D5–D6 | 动态负载测试 | batch size 在 1–32 随机变化 | 动态场景对比 |
| D7 | 长上下文测试 | 在模型有效上下文范围内，使 KV Cache 需求超过 12 GB 显存承载能力 | 换出能力验证 |

**测试矩阵**：

| 场景 | 参数 | 主要指标 |
|------|------|----------|
| 固定 BS=1 | 512 tokens 输入 / 128 tokens 输出 | TTFT、TPOT、P99 延迟 |
| 固定 BS=8 | 同上 | 吞吐量、显存占用、P99 延迟 |
| 固定 BS=32 | 同上 | 吞吐量、显存占用 |
| 动态 BS | batch size 1–32 随机 | P99 延迟、CUDA Graph 命中率、回退率 |
| 长上下文 | 模型原生支持 ≥16K 时使用 16K tokens 输入；否则用模型最大有效长度或合成负载 | 是否 OOM、TTFT、显存峰值 |

**测量方法**：

- Nsight Systems：抓取 CUDA、NVTX、OS 运行时 trace，定位映射与重放的耗时。
- `nvidia-smi`：以 0.5 秒间隔监控显存占用。
- 自定义 NVTX 标记：在推理阶段、映射阶段、解映射阶段打点。
- 所有测试至少重复 10 次，报告均值与 P99。

**预期假设（以实测为准）**：

| 指标 | vLLM/`cudaMalloc` 基线 | Sepia | 预期差异 |
|------|--------------------------|-------|----------|
| 固定 BS=8 P99 | 45 ms | 42 ms | -6.7% |
| 动态 BS P99 | 72 ms（频繁回退） | 50 ms | -30.6% |
| 长上下文（模型有效长度内） | 视显存预算：基线可能 OOM | 应能完成；峰值显存更低仅限换出/按需映射场景 | 以实测为准 |
| CUDA Graph 命中率 | ~60% | ~98% | +38pp |

## 8. 风险与应对

| 风险 | 影响 | 应对方案 |
|------|------|----------|
| RTX 4070 显存仅 12 GB | 无法完整测试 7B 以上模型 | 先用 GPT-2 验证方案；7B 使用量化版本；长上下文测试选用原生支持目标长度的模型，或使用合成 KV Cache 负载单独验证换出能力 |
| `cuMemMap` 延迟过高 | 性能不达标 | 延迟解映射：保留映射缓存，减少映射/解映射次数 |
| CUDA Graph 捕获复杂 | 集成难度大 | 先单层/小模型，逐步扩展到全模型 |
| vLLM 耦合度高 | 难以替换内存管理 | 先做独立 Demo，再定义最小集成接口 |
| 驱动/API 兼容问题 | 示例编译失败 | 锁定 CUDA 12.x + 驱动 535+，记录版本矩阵 |
| 显存泄漏难定位 | 测试不可靠 | 用 `nvidia-smi` 监控 + 映射表状态打印 + 单元测试隔离 |
| 基线结果受环境波动影响 | 对比失真 | 固定时钟、关后台任务、多次重复取均值与 P99 |

## 9. 语言与工具选型

| 类别 | 选型 | 用途 |
|------|------|------|
| 语言 | C++17 | `VMMAllocator`、`KVBlockManager`、CUDA Driver API 封装、演示程序 |
| 语言 | CUDA C++（`nvcc`） | 自定义 kernel：显存读写测试、KV Cache 访问、可能的融合算子 |
| 语言 | Python 3.10+ | PyTorch 基线、vLLM 集成与基准脚本、数据分析与绘图 |
| 语言 | CMake 脚本 | 构建配置 |
| 构建 | CMake ≥ 3.20 + Ninja | 项目构建与依赖组织 |
| 测试 | CTest + GoogleTest | 单元测试、重复分配/释放压力测试 |
| 性能分析 | Nsight Systems | 抓取 CUDA/NVTX/OS trace，定位映射与重放耗时 |
| 显存监控 | `nvidia-smi` | 观测显存峰值与泄漏 |
| 参考实现 | vLLM、SGLang 源码 | 理解 KV Cache 管理与 RadixAttention |
| 模型 | PyTorch + Hugging Face Transformers | GPT-2、量化 LLaMA3-8B、长上下文候选模型 |
| 版本管理 | Git / GitHub | 代码与文档版本管理 |

说明：

- 核心内存管理层用 C++ 实现，避免 Python 层的性能与 GIL 干扰；Python 只用于测试、基准驱动和结果分析。
- CUDA VMM API 属于 CUDA Driver API，C++ 链接 `libcuda.so`，不使用 CUDA Runtime 的 `cudaMalloc` 管理 KV Cache。
- 单元测试优先采用 GoogleTest；若安装受限，可先用 CTest + 简单断言替代，不阻塞开发。
